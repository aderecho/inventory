# Coding Standards and Project Structure

**Technology stack:** Laravel 12.63 (backend), Vue 3.5.21 (frontend)

## Purpose

These rules guide AI coding agents and developers when implementing or
modifying features. Prefer extending the existing architecture over
introducing competing patterns. Inspect relevant files and project
conventions before making changes.

## Core principles

1.  **Inspect before implementing.** Search for existing
    implementations, related modules, naming conventions, routes, tests,
    and shared utilities.
2.  **Reuse before creating.** Extend suitable existing services,
    requests, policies, composables, components, and layouts rather than
    duplicating them.
3.  **Keep changes focused.** Do not refactor unrelated features or
    introduce unnecessary abstractions.
4.  **Preserve behavior.** Avoid breaking existing APIs, database data,
    permissions, and UI flows.
5.  **Test meaningful behavior.** Add or update automated tests and
    report actual results.
6.  **Do not assume missing functionality.** Verify whether a
    requirement is already satisfied before adding code.

## Code cleanliness and minimal implementation

- Generate only code necessary to meet the current requirements and acceptance criteria. Do not add speculative features, placeholder implementations, unused helpers, unnecessary dependencies, or boilerplate without a purpose.
- Prefer straightforward, readable solutions over excessive abstractions, layers, indirection, or defensive checks that do not address a realistic failure case.
- Remove unused imports, variables, functions, unreachable branches, duplicate logic, and obsolete commented-out code in files being changed, when safe.
- Remove comments that merely repeat what clear code already says, including noisy line-by-line narration and autogenerated filler comments.
- Keep comments that explain **why** a non-obvious decision exists, important business rules, security considerations, performance constraints, workarounds, and surprising edge cases.
- Preserve license and copyright notices, required annotations, public API documentation, and comments with meaningful operational or maintenance value.
- Do not delete unrelated comments or code solely to make a file shorter. Confirm that removals do not change behavior, interfaces, or tests.
- Avoid unnecessary logging, broad exception catches, unused configuration, and redundant validation; retain checks required for security, correctness, or clear error handling.
- Prefer editing an existing suitable file over creating a new file unless separation improves clarity or reuse.
- Before finishing, review the diff for accidental additions, unused code, redundant comments, and unrelated changes.

## Backend --- Laravel 12.63

### Controllers

-   Keep controllers thin: receive validated input, authorize actions,
    delegate business operations, and return appropriate responses.
-   Do not place complex business rules, multi-step database operations,
    or large queries in controllers.
-   Use dependency injection for services.
-   Follow existing API response conventions; do not introduce a new
    response wrapper without a reason.

### Services and business logic

-   Place business workflows and reusable domain logic in appropriately
    named service classes, following the existing directory structure
    (for example, `app/Services`).
-   Keep services focused on one coherent responsibility.
-   Use database transactions for operations that must succeed or fail
    together.
-   Handle errors deliberately; do not silently swallow exceptions.
-   Avoid creating a service for trivial framework calls when it adds no
    value.

### Validation and Form Requests

-   Create or reuse Laravel Form Request classes for endpoint validation
    (for example, `StoreItemRequest`, `UpdateItemRequest`).
-   Inspect existing requests before adding new ones; share common rules
    where practical.
-   Use `authorize()` appropriately and ensure actual access control is
    enforced.
-   Validate types, lengths, ranges, identifiers, uniqueness, and
    relationships as applicable.
-   Do not rely on frontend validation for security.

### Migrations and database changes

**Before creating any migration:** 1. Inspect existing migrations, the
current schema, and related models. 2. Check whether the intended table,
column, index, constraint, or relationship already exists. 3. Confirm
naming and database conventions. 4. Create a new migration only when an
actual schema change is required.

-   Never edit previously applied migrations to change a deployed
    schema; create a new migration instead.
-   Prefer additive, backward-compatible changes when feasible.
-   Include appropriate foreign keys, indexes, uniqueness constraints,
    nullability, and defaults.
-   Consider existing data and rollback behavior before destructive
    changes.
-   Do not drop columns or tables without explicit approval.

### Models and relationships

-   Inspect relevant models and their existing relationships before
    modifying them.
-   Reuse established Eloquent relationships and naming conventions.
-   Ensure foreign keys, relationship types, and database constraints
    agree.
-   Avoid redundant relationships and duplicate model logic.
-   Guard mass assignment with appropriate `$fillable` or `$guarded`
    configuration.
-   Avoid N+1 queries through appropriate eager loading when needed.

### Security: verify first, add only what is missing

-   Inspect existing authentication, authorization, policies, gates,
    middleware, rate limits, validation, CSRF protections, and security
    configuration before making changes.
-   **Do not add duplicate security layers or replace working security
    mechanisms without a demonstrated gap.**
-   Enforce permissions on the server for protected actions and records.
-   Use Eloquent/query bindings rather than interpolating untrusted SQL.
-   Prevent mass-assignment, insecure direct object reference, unsafe
    file upload, and sensitive-data exposure issues.
-   Keep secrets out of source control and logs.
-   Use existing authentication and session/token strategies; do not
    install another package without a clear requirement.
-   When a security gap is found, describe it and apply the smallest
    compatible fix.
-   Do not claim that security is complete solely because a checklist
    was followed.

### Backend tests

-   Add or update PHPUnit/Pest tests using the project's existing test
    framework.
-   Cover successful operations, validation failures, unauthorized
    access, forbidden access, and important edge cases.
-   Test business rules at the appropriate level and HTTP/database
    behavior with feature tests.
-   For stock or financial-like quantities, test invariants,
    concurrency-sensitive operations where relevant, and transaction
    rollback.
-   Run the relevant tests and report pass/fail results; do not
    fabricate evidence.

## Frontend --- Vue 3.5.21

### Composition API and conventions

-   Follow the existing Vue 3 code style and project conventions.
-   Prefer Composition API and `<script setup>` for new Single File
    Components unless the project has a different established
    convention.
-   Keep presentation, shared stateful logic, and API access
    appropriately separated.

### Composables

-   **Before creating a composable, inspect existing composables and
    related features.**
-   Extract logic into a composable when it is genuinely reused,
    expected to be reused across related features, or meaningfully
    simplifies a complex component.
-   Use names such as `usePagination`, `useFilters`, or domain-specific
    `useInventoryItems`.
-   Keep composables focused, with clear inputs, outputs, reactive
    state, and lifecycle handling.
-   Do not extract one-off trivial logic solely to create more files.
-   Reuse existing API clients, stores, and utilities rather than
    creating parallel implementations.

### Reusable components

-   Inspect existing components before creating new ones.
-   Build configurable components for repeated patterns such as tables,
    filters, forms, dialogs, confirmations, status displays, and
    pagination.
-   Use props, emits, and slots to support variation without duplicating
    markup.
-   Keep components cohesive; avoid overly generic components with many
    unrelated modes.
-   Preserve accessibility, loading/empty/error states, and consistent
    UI behavior.
-   Keep domain-specific behavior out of generic UI components where
    practical.

### Reusable layouts

-   Inspect existing application layouts and navigation structure before
    adding layouts.
-   Reuse shared shells for navigation, headers, sidebars, content
    containers, and responsive behavior.
-   Use nested routes/layouts or slots where appropriate rather than
    duplicating page scaffolding.
-   Create a new layout only when the user experience or structural
    requirements genuinely differ.
-   Keep responsive behavior and accessibility consistent.

### Frontend tests

-   Add or update tests using the test tools already configured in the
    project.
-   Test shared composables and components, especially their public
    behavior and important states.
-   Cover critical user flows and error handling where suitable.
-   Do not install new testing frameworks without checking what already
    exists.

## Workflow for every feature or change

1.  Read the task and acceptance criteria.
2.  Inspect existing routes, controllers, requests, services, models,
    migrations, tests, frontend composables, components, and layouts
    relevant to the task.
3.  Summarize what already exists and identify what is missing.
4.  Choose the smallest change that follows the existing architecture.
5.  Implement backend validation, business logic, authorization, and
    persistence as needed.
6.  Implement frontend logic using existing composables, components, and
    layouts where possible.
7.  Add or update tests for changed behavior.
8.  Run relevant tests, linters, and builds where available.
9.  Report files changed, tests run, results, and any remaining risks.
10. Mark a task complete only after its acceptance criteria are
    verified.

## Rules for AI coding agents

-   Do not create duplicate migrations, relationships, services,
    requests, security controls, composables, components, or layouts.
-   Do not claim something is absent without checking the repository.
-   Do not introduce a new architectural pattern merely because it is
    popular.
-   Ask before destructive schema changes or major cross-cutting
    refactors.
-   Do not change unrelated code without a concrete dependency.
-   Never report tests as passed unless they were actually executed and
    passed.
-   If existing implementation conflicts with these guidelines, explain
    the tradeoff and prefer a minimal compatible change unless
    instructed otherwise.
